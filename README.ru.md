# cli-MMA-client

[English](README.en.md) | **Русский** | [简体中文](README.md)

Консольный клиент для протокола [MMA](https://github.com/Edestuss0/MMA) — бинарного протокола «запрос–ответ» и каналов поверх TCP. Клиент собирает кадр MMA по локальному конфигу, отправляет его серверу и выводит payload ответа.

> **Статус: ранняя разработка.** Запрос (route, payload, адрес сервера) зашит в `main()`. См. [Текущие ограничения](#текущие-ограничения).

## Как это работает

У MMA нет фиксированного формата на проводе. Раскладка байтов каждого кадра описывается общим `FramerConfig`, поэтому клиент и сервер понимают друг друга, только если используют **одну и ту же раскладку**. Этот клиент читает раскладку из файла `framer.cfg` при запуске.

Кадр состоит из:

- **Заголовка** (`header_length` байт): опкод, версия, длина route и число options (по одному байту на настраиваемых позициях), а также три 32-битных поля в big-endian: длина options, длина payload и ID запроса.
- **Тела**: route, options и payload в настраиваемом порядке.

Полная спецификация (опкоды, кодирование options, обработка ошибок) находится в [репозитории протокола](https://github.com/Edestuss0/MMA).

## Требования

- Компилятор C++20 (GCC или Clang; MinGW-w64 для сборки под Windows)
- CMake 3.15 или новее
- [Asio](https://think-async.com/Asio/) (standalone, только заголовки). `asio.hpp` должен быть в путях поиска заголовков компилятора: проект CMake его не скачивает.

```bash
sudo apt install libasio-dev   # Debian / Ubuntu
brew install asio              # macOS
```

## Сборка

```bash
cmake -S . -B build
cmake --build build
```

Бинарник: `build/MMA_client`.

Кросс-компиляция под Windows (MinGW-w64, статическая линковка; заголовки Asio должны быть видны и компилятору MinGW):

```bash
cmake -S . -B build-win -DCMAKE_TOOLCHAIN_FILE=cmake/windows.cmake
cmake --build build-win
```

## Конфигурация

Клиент читает `framer.cfg` из **текущей рабочей директории**. Начните с готового примера:

```bash
cp framer.cfg.example framer.cfg
```

Синтаксис намеренно минимальный:

- одна настройка на строку: `ключ значение` (один пробел между ними), строка заканчивается переносом;
- значения — целые неотрицательные числа;
- **никаких пустых строк, комментариев и неизвестных ключей.** Парсер их не обрабатывает, и клиент упадёт.

В `framer.cfg.example` лежит раскладка MMA по умолчанию:

```
header_length 29
opcode_pos 1
version_pos 2
route_len_pos 3
options_count_pos 4
big_bytes_config.options 1
big_bytes_config.payload 2
big_bytes_config.req_id 3
body_orders.route 1
body_orders.options 2
body_orders.payload 3
max_message_length 10000000
```

| Ключ | Значение |
| --- | --- |
| `header_length` | Полный размер заголовка в байтах. |
| `opcode_pos`, `version_pos`, `route_len_pos`, `options_count_pos` | Позиция соответствующего однобайтового поля заголовка, **считая с 1** (`opcode_pos 1` — первый байт заголовка). |
| `big_bytes_config.options` | Слот (1–3) 4-байтового поля *длина options* (big-endian). |
| `big_bytes_config.payload` | Слот (1–3) 4-байтового поля *длина payload* (big-endian). |
| `big_bytes_config.req_id` | Слот (1–3) 4-байтового поля *ID запроса* (big-endian). |
| `body_orders.route`, `body_orders.options`, `body_orders.payload` | Позиция (1–3) каждой секции в теле. Каждое значение 1–3 должно встречаться ровно один раз. |

Три 4-байтовых поля занимают последние 12 байт заголовка. Слот *n* начинается со смещения `header_length - 12 + 4 * (n - 1)` байт (отсчёт с 0). Значения трёх `big_bytes_config.*` тоже должны быть числами 1, 2 и 3 в каком-то порядке.

Ключи `max_message_length`, `options_key_first`, `options_len_order`, `payload_len_order` и `req_id_order` парсер принимает, но пока не использует.

Значения должны совпадать с `FramerConfig` сервера, иначе сервер не сможет разобрать кадр.

## Использование

```bash
./build/MMA_client
```

Клиент читает `framer.cfg`, отправляет серверу один запрос `Once` (опкод 2), выводит отправленный пакет в hex, а затем payload ответа.

## Текущие ограничения

- Запрос зашит в `main()`: route `POW`, payload `21`, ID запроса `1`, сервер `0.0.0.0:8080`. Чтобы изменить, отредактируйте код и пересоберите. Для локального сервера используйте `127.0.0.1`: подключение к `0.0.0.0` не переносимо (на Windows оно не работает).
- Options не отправляются (их число всегда 0), а options в ответах игнорируются.
- Выводится только payload ответа, опкод ответа не интерпретируется.
- Используется только опкод запроса `Once`. `ChannelConnect` и `ChannelMessage` не реализованы.
- TLS нет. Сам MMA не даёт ни шифрования, ни аутентификации, поэтому используйте доверенную сеть или туннелируйте соединение через TLS.

## Структура репозитория

| Путь | Описание |
| --- | --- |
| `main.cpp` | Клиент (цель CMake `MMA_client`). |
| `includes/conf.hpp` | `MmaFramerConfig` и константы протокола (опкоды, версия). |
| `includes/tools.hpp` | Функции чтения и записи big-endian. |
| `cmake/windows.cmake` | Toolchain-файл MinGW-w64 для сборки под Windows. |
| `framer.cfg.example` | Пример конфига клиента (раскладка MMA по умолчанию). |
| `main_alt.cpp` | Экспериментальный клиент только для POSIX с флагами командной строки. В сборку CMake не входит. |
| `server_kfg` | Пример конфигурации MMA-сервера (другой формат; этим клиентом не читается). |
